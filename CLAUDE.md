# Working on this fork

Notes that are true of this repository whoever is working in it. Machine-specific paths are
kept out on purpose - only the shape of the rule is here.

## The release build silently drops the ScreenScraper credentials

`chome_ss.cpp` gets the application's ScreenScraper devid and devpassword from
`bin/ss_credentials.h`. That header is **regenerated by the Makefile at parse time** from
`$(SS_ENV)` (default `$HOME/.config/classicui/ss.env`), and `ss_creds.sh` **deletes it when
that file is absent**.

So a build in a container - where `$HOME` is `/root` and the developer's env file is not
mounted - produces a firmware with the scraper gate shut. No cover art downloads for anyone.
There is no error: the build log, the ELF type, the firmware's own marker strings and the md5
check all look exactly like a good build. Pre-generating the header on the host does not help
either, because the next `make` inside the container removes it again.

A containerised release build therefore MUST mount the env file and name it:

```
docker run ... -v "$HOME/.config/classicui/ss.env:/ss.env:ro" ...  make SS_ENV=/ss.env ...
```

`make_sdcard_root.sh` now refuses to package a firmware that has no devid in it, which is the
only reason this is caught rather than shipped. `--no-ss-creds` is how a firmware that is
*meant* to have no scraper (the SNAC-only build) says so.

Do not put the credentials on a compiler command line. A `-D` puts the password in every build
log and in `ps` while the compiler runs. For the same reason, code that checks a binary for the
devid must hand it to `grep` on **stdin** (`grep -F -f -`), never in argv.

Several comments in `chome_ss.cpp` still say the credentials are "undefined in every build we
ship". That was the old policy. Shipped builds carry them; the player's own account is separate
and comes from `MiSTer.ini` at runtime.

## Releases are cut from a tag, not from master

The fork's `master` is a plain upstream mirror and is far behind the work. Every Classic Home
release is a tag on the branch that produced it, with the SD-card archive attached. Do not
assume a release means master moved - it never has.

`make_sdcard_root.sh` requires `--expect-md5` and will not read `bin/MiSTer` for you. That is
deliberate: beta 2 nearly shipped a rebuild nobody had tested, under notes describing hardware
tests of a different binary. Quote the md5 of the build you actually tested.

## Branches worth keeping

- **`snac-pr`** - PSX controllers over SNAC on stock MiSTer, nothing else. The branch an
  upstream pull request would come from.
- **`deploy-all`** - everything: the front-end, SNAC, the analog takeover. This is the release
  line. `disc-shelf` is its working tip; `deploy-all` trails it.
- The analog/RGB-SCART work (reaching the menu without going through the VGA config, the
  `fb_terminal_vga` takeover) is **already merged into the `disc-shelf`/`deploy-all` line** and
  is not a separate branch any more.

Everything else under `disc-*`, `snac-wave*`, `worktree-agent-*` is a merged feature branch or
an agent's scratch worktree and can go.

## `make clean` after touching a header

Incremental make in this tree does not reliably rebuild after a header changes or after a
branch switch, and the result is a binary containing two different struct layouts - which
presents as a setting being read as 0 in one file and 1 in another. Check with
`find bin -name '*.o' ! -newer <header>`; anything but empty means the binary is untrustworthy.

## Capturing the screen off a device

`support/classicui/tools/fbgrab.c` reads the framebuffer out of `/dev/mem`. Two traps:

- **The geometry is not always the module's.** With the analog takeover on, the front-end draws
  buffer 1 at 320x240 and `/sys/module/MiSTer_fb/parameters/*` agrees. With it off, it draws
  **buffer 2** at half the mode (640x360 inside 1280x720) and the parameters still say
  1280x720. Reading the smaller frame at the larger size does not fail - it produces a smear of
  the frame repeated four times across, which looks like a rendering bug in the front-end. The
  firmware's own log line is the authority: `video: mode now 1280x720, fb 2 at 640x360`.
- **Double buffering.** A capture identical to the previous one is the first thing to distrust,
  not evidence that a keypress was ignored.

And a timing trap that is not the tool's fault: the in-game **Close Game** confirm expires after
three seconds, which is shorter than a capture round trip. Send both presses in one `keyinj`
invocation or the second one lands on a disarmed row and the game stays open.
