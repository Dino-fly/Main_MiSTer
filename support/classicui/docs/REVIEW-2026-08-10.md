# Full review — Classic Home and PSX SNAC, 2026-08-10

Reviewed: branch `classic-ui` at dfa6a21, against upstream merge-base af770c5.
Method: the host harness was run in full (2425 checks, 0 failures, ~6 minutes in
Docker); every diff to a shared upstream file was read line by line; `snacpad.cpp`,
`chome_ini.cpp`'s writer, the two layout guards and the ranked findings below were
verified directly; the five outside-world modules (disc, rip, ss, net, bt), the
fourteen-thousand-line `chome_ui.cpp` and the 21.7k-line harness were audited in
depth by three parallel read-only passes whose top claims I re-verified against the
source before ranking them here. Roughly: I read ~8k lines closely, the audits read
the other ~50k, and everything marked **verified** below was traced to the cited
line by someone who read it — nothing in this document is repeated from a commit
message or a doc. The captured frames in `test/out/` were viewed as images, with
the 240p set given priority.

---

## 1. Verdict

**The code is reliable — more reliable than most shipping firmware — with three
specific exceptions, and the tests are genuinely good with one specific hole in
the two guards you lean on hardest.**

The exceptions: (1) an out-of-bounds read in the fallback card renderer that
draws stack garbage for long titles, most reachable at 240p; (2) a consistent
failure to reap forked children — one zombie per disc launch, per rip cancel,
per Bluetooth pairing session, and a window where two `btctl` agents fight over
one adapter; (3) the library scan's "one slice per frame" is actually one whole
*system* per frame, so first boot and every Rescan Library freezes the UI for
seconds per system on a big zip library — invisible in CPU% because the firmware
busy-polls, exactly the trap this project already knows about. Everything else
found is smaller than these three.

On the tests: the suite is real — assertions against real invariants, fixtures
made deliberately hostile, and the fix-with-a-failing-test habit is **verifiably
long-standing, not recent** (sampled fix commits across the whole history touch
the harness in the same commit; the two documented sabotage checks are in the
code). But the run-wide "no row is hidden" guard has most of its evidence wiped
by a `chome_rowdrop_clear()` left inside a mid-suite section, and both guards
fail *open*: if the source corpus fails to load, or nothing gets recorded, they
pass vacuously. The known 240p legend-overlap gap is one member of a family —
neither guard encodes any *cross-element* geometry at all.

The testing procedure (Mac first, device for what needs hardware) is not just a
habit here, it is institutionalised — TEST-PLAN.md is a scripted device session,
unverified work is labelled "unverified, in those words", and the harness's own
comments record when a stub was made worse on purpose. Its two real weaknesses:
there is no CI, and the one device is analog-only — so the HDMI path has never
been on real glass, while GUIDE.md tells users "HDMI only — Good, confirmed."
That contradiction should be fixed before it costs a user a day.

UX is strong and genuinely controller-first; 240p is close to first-class. Copy
is the best I have seen in a hobby firmware. The one missing feature a player
will actually feel is **search** — on a thousand-game shelf, letter-jump is the
only tool. And two of the five offered sort modes silently do nothing distinct.

Upstream divergence is far healthier than believed: **89 deleted lines** against
upstream, not 9k (see §9), and the shared-file changes are gated, documented and
in three cases upstreamable fixes.

## 2. Ranked findings

Worst first. **[verified]** = traced in source at the cited lines (by me or by an
audit pass whose claim I re-checked); **[suspected]** = inferred, needs a run or
the device to confirm.

### R1. Out-of-bounds read in the fallback card's title wrap — [verified]
`chome_ui.cpp:1347-1358`. When a title wraps past five lines the loop breaks
with `nl == 5`, the unconditional `nl++` at :1358 makes it 6, and the draw loop
at :1362 reads `lines[5]` — one row past `char lines[5][CH_TITLE_LEN]`. It
renders uninitialised stack as a sixth title row. Read-only, so it garbles a
card rather than crashing; most reachable at 240p (narrow `avail`) with a long
No-Intro name and no cover art — i.e. precisely the plain-plate case the
function exists for. The same bug was found and fixed in `wrap_text()`
(:3008-3060, with a comment describing it); this site never got the fix. *Do:*
apply the same fix; add a harness card with a seven-line title at `lo` and
assert the composed frame is stable across two renders.

### R2. Forked children are not reaped — a zombie per routine action — [verified]
Three sites, one shape, no `SIGCHLD` handler or `waitpid(-1)` sweep anywhere in
the tree to catch what they drop:

- `chome_disc.cpp:1052-1057` — `disc_watch_stop()` does `kill(SIGKILL)` then
  `waitpid(..., WNOHANG)` then `helper_pid = -1`. WNOHANG immediately after
  SIGKILL essentially never reaps (the child has not died yet, and in the
  stuck-ioctl case the comment itself cites, it *cannot* die yet), and dropping
  the pid means nothing ever reaps it. This runs before **every** disc launch
  and every rip — a zombie per launch, on the happy path.
- `chome_rip.cpp:1287-1289` — same pattern in `rip_cancel()`.
- `chome_bt.cpp:561-578` — `pair_child_stop()` kills the pairing group and never
  waits; it also sets `pairing = 0`, which makes the only reap site
  (`bt_poll()`'s `if (pairing)` block, :756-777) unreachable for that pid
  forever. And `bt_pair_start()` (:510-511) guards on `pairing`, not on
  `pair_child > 0`, so the next "Add controller" overwrites the pid — the old
  process becomes unreapable *and*, since SIGINT is a polite stop, there is a
  window with **two `btctl pair` agents on one adapter**, both having opened the
  same output file with `O_TRUNC`.

Zombies survive the core-switch re-exec (exec keeps the process, so it keeps
its children). Bounded per session by user actions, but a long evening of disc
swapping and pad pairing accumulates real process-table entries, and the double
`btctl` is a functional bug (it is the "re-pair destroys the pairing" failure
the comment at chome_bt.cpp:555-559 warns about, self-inflicted). *Do:* one
shape of fix for all three — never discard a pid before `waitpid` has actually
returned it; keep a small "dying" list reaped from the polls that already run
every frame. Your own memory note ("kill child processes") is half of this
lesson; the other half is *reap* them.

### R3. The library scan's slice is a whole system, not a frame's worth — [verified structure; magnitude suspected]
`chome_lib.cpp:1239-1268`: `lib_scan_step()` is documented as one slice per
frame, but the slice is `scan_dir()` over one **entire system** — a full
recursive walk, a second `opendir` per directory (`dir_has_playlist`, :1150),
and, worst, `zip_playables()` (:352-372) opening **every `.zip`'s central
directory** off the SD card, thousands of opens in one call from the frame loop
(`chome_ui.cpp:13984-13990`). On first boot, and on the user-facing **Rescan
Library** row every time, the UI hangs for seconds per large system. Because
the firmware busy-polls at 100% of a core, this is invisible in CPU time — the
project's own documented trap. The index cache hides it on ordinary boots,
which is why it has not been felt. *Do:* bound the slice (per-directory or
per-N-entries — the `scan_sys` cursor already half-supports it), and time a
Rescan on the device with a 2-3000-zip SNES folder to size the problem
honestly.

### R4. The two load-bearing guards are weaker than their names — [verified]
The brief believed these two guards are load-bearing. They are — which is why
this matters:

- **Half the run's row-drop evidence is destroyed before it is read.**
  `harness.cpp:9997` calls `chome_rowdrop_clear()` inside
  `assert_long_core_list_scrolls()`'s per-canvas loop; the run-wide
  `assert_no_row_is_hidden()` (:18286) reads the accumulator only at :21693.
  Everything recorded by the ~60 sections before :9997 is gone; the guard's
  actual coverage is "sections after it, plus what `sweep_screens()`
  re-composes". The section's own closing comment (:10047-10051) says the log
  is deliberately *not* cleared on the way out — nobody noticed the clear on
  the way in.
- **Both guards fail open.** `clipsrc_load()` (:18001) prints a warning and
  gives up if `support/classicui` is not under the cwd; `text_is_ours()` then
  returns 0 for everything and every cut sentence is waved through as a game
  name — `check(ours == 0)` passes vacuously. Neither guard asserts a minimum
  number of records or screens was seen; a refactor that stopped routing text
  through `gfx_clip()` would turn both green forever.

*Do:* delete the clear at :9997 (the section already takes a per-section
snapshot via `chome_rowdrop_n()` before/after if it needs one); assert the
corpus loaded and that `text_is_ours()` recognises one known sentence; assert a
floor on records seen (e.g. `n > 500` clip records, `sweep` composed ≥ N
screens). Then revert the fix for one known-caught bug and watch it fail — the
project's own standard.

### R5. Other gaps of the legend-overlap shape — the guards encode no cross-element geometry — [verified]
The known gap (a panel grown by a row overlapping the legend at 240p, invisible
to both guards) is one instance of a family, because both guards measure
elements against **themselves**:

- `assert_no_row_is_hidden` checks rows against the panel's *own* bottom
  (`b->y + b->h`, chome_ui.cpp:3135). Nothing anywhere asserts panel rectangles
  against `y_legend`, against each other, or against the canvas.
- In `draw_rows_c_at()` (:3126-3183) the row *label* goes through `marq_fit`,
  but the **value is drawn unclipped** at the right edge — a value wider than
  the row paints leftwards under the label with no clip record. No test covers
  it.
- Overscan is enforced per-element, at 240p only, for four enumerated elements
  (`assert_overscan`, harness.cpp:13598-13725). No global "nothing bright
  inside the margin while any dialog is up" sweep; a new dialog leaking into
  the safe area passes.
- The footer help under a focused row is not a "row" to the counter and can
  extend past the panel unrecorded; the SNAC help is covered only because a
  section manually parks the cursor on it in two passes (:10006-10029) —
  coverage by choreography, not instrumentation.
- The clip-sweep navigates by hardcoded row indices (`rows[] = {1,5,6,7,8}`,
  :18184); a menu reorder silently points the sweep at different panels and
  nothing fails. `rowdrops[32]` drops the 33rd site silently
  (chome_ui.cpp:3085).

*Do:* one new invariant pays for most of this: after every composed screen in
the sweep, assert no opaque draw intersects the legend band or the overscan
margin, and that sibling panel rects are disjoint. The compose layer already
knows every rect it painted (the damage machinery proves it); recording them in
`CHOME_HOST_TEST` builds is a small step.

### R6. Two open, player-facing device bugs are already on the books — [verified as documented; behaviour needs the device]
TEST-PLAN.md carries two unresolved defects on the release line: **A1**, the
analog takeover stays held after the menu closes (`fb params` pinned at
320×240 with the game running — confirmed from the log side, unknown whether
visible on glass); and **A4**, a PSX suspend point saves but does not load
(the log shows the load issued; whatever fails is downstream). Both are
player-facing on the analog path, which is the *primary* path. They pre-date
this review; they belong in it because a review of reliability that ignored
the two known live bugs would be dishonest. *Do:* they are the first hour of
the next device session, and the plan for that hour is already written.

### R7. Documentation states things that are not true — [verified]
Four contradictions, each cheap to fix and each capable of misdirecting a user
or a future session:

- **GUIDE.md:326 "HDMI only — Good, confirmed"** vs RELEASE-NOTES-v5.md:193
  "Everything above 240p is verified in the test harness only. There is no
  HDMI display here… never been seen on a real panel." One of these is false.
  Given the device is analog-only, the GUIDE row overstates, and it is the one
  users read.
- **README.md:1256-1343**: the whole ScreenScraper section still says the
  module is "written but inert, pending a credential" and that no shipped
  build carries a devid. CLAUDE.md says the opposite is now policy, and
  GUIDE.md:610 agrees ("The published builds carry one"). The stale
  copies: chome_ss.cpp:49-51, chome_ss.h:21-23, :32-36, :41-43, :285-287 —
  five comment sites still describing the old policy, exactly as CLAUDE.md
  warns. Dangerous shape: someone reasoning from "provably dead code" will
  relax about a path that is now live.
- **main.cpp:~100** (the idle-sleep comment) says `chome_core_idle()`
  *excludes* an in-game menu over a still-running core. The implementation
  (chome_ui.cpp:12829-12856) deliberately **includes** it and documents why the
  old exclusion was wrong. The main.cpp comment describes the reverted design.
- **UPSTREAM.md** says "491 checks" (it is 2425) and "Eight keys" (there are
  sixteen `classicui_*` keys plus five `snac_*`). The document is the fork's
  best asset for a future merge; stale numbers teach readers to distrust it.

### R8. Two of five sort modes silently do nothing distinct — [verified]
`chome_lib.cpp:1644-1659`: `cmp_entry()` has no case for `SORT_ADDED` — the
Sort panel offers "Recently Added" and delivers Title A-Z. And `SORT_RECENT`'s
case is byte-identical to `SORT_PLAYS` (both compare play counts), so
"Recently Played" as a *sort* duplicates "Most Played" (distinct from the
properly-ordered Recently Played *view*, which works). A feature presented as
working, that isn't. *Do:* either implement (`chome_item` has no added-date;
the index cache could stamp first-seen) or remove the rows until they exist —
the front-end's own design language ("a greyed-out row that could never work"
is called out in GUIDE.md as a thing you refuse to ship) decides this one.

### R9. Expired two-press confirmations keep their armed UI on screen — [verified]
The design rule is written at chome_ui.cpp:13105-13111 ("a confirmation with a
timer needs a repaint while it is up and one more when it runs out") and
implemented only for `co_promoted` (:13113-13117) and the pad-test back-arm
(:13974). At least eight other armed confirms — power restart/shutdown
(`pwr_until`, drawn :7623-7649), suspend-delete (`del_arm_until`), settings
save/discard, covers, Best Settings (`ini_until`), pad-forget, rip stop and
rip overwrite — evaluate `CheckTimer` at draw time but nothing requests the
expiry repaint, so "Press again to delete" stays on screen indefinitely after
the window has closed. Every accept path re-checks the timer (verified), so
the failure is in the safe direction — the stale press re-arms instead of
acting — but the screen shows a live destructive prompt that is a lie, and the
press that looks like a confirm silently restarts the countdown. *Do:* the
shared fix the code already describes for `co_promoted`: one registered
deadline that `mark_dirty()`s once on expiry.

### R10. MGL writer does not XML-escape the game path — [suspected, five-minute test]
`chome_ui.cpp:9075`: `relpath` is printed raw into `path="…"`. `"Sonic &
Knuckles (World).md"` produces invalid XML; a `'` or stray `&` is common in
ROM names. Whether launch actually fails depends on how lenient the firmware's
MGL parse is with a raw `&` — untraced, because the loader is outside the
harness. *Do:* put an `&`-named ROM on the card and launch it. If it fails,
escape `&`, `"`, `'` at the write site (five lines).

### R11. Disc/net helpers can hang their feature for the session, silently — [verified structure]
- `chome_disc.cpp`: a helper wedged in an uninterruptible ioctl mid-identify
  has already published `DISC_SPINNING` and will neither exit nor publish
  again; `disc_poll()` (:1096-1191) has no deadline on SPINNING, so the UI
  shows "Reading the disc" forever with no message. The two-strike refork
  logic covers a helper that *dies*, not one that *wedges* — the design's own
  documented scenario (chome_disc.h:20-30).
- `chome_net.cpp`: a join child has deliberately no kill deadline (:740 — it
  holds the only copy of the old config, good reason), but the module is
  single-child and `net_poll()` refuses all work while one exists (:866), so
  an `ifup`/`ifdown` that never returns leaves the Wi-Fi screen dead for the
  session, stuck saying "Restarting Wi-Fi".

*Do:* a deadline on SPINNING that changes the message ("The drive is not
answering — unplug it to reset"), and for net a very long (minutes) last-resort
deadline that gives the screen back with an honest "the join never finished".

### R12. `suspend.txt` is opened on every composed frame of the shelf — [verified]
`chome_ui.cpp:2803` → `susp_matches()` → `susp_read()` (:11223):
fopen/fgets×3/fclose of a card file inside `build_legend`, which runs on every
rendered frame — including every marquee step and every band of a slide. Page
cache makes it cheap, but it is unbounded filesystem I/O in the render path of
a codebase that is otherwise scrupulous about exactly this (`sync_sel_slots`'s
"four stat() calls, only on change" is thirty lines away). All writers are in
the same file; cache on a change flag. Same family, smaller: `rip_poll()`
fopens its progress file per frame with no skip counter, where `disc_poll()`
skips 31 of 32.

### R13. The config report can truncate mid-sentence and its own truncation marker is unreachable — [verified]
`chome_cfgrec.cpp:210-224`: `put()` saturates `pos` at `max-1` *after*
`vsnprintf` has partially written the overflowing line — the buffer ends
mid-sentence, which the block comment above it promises it never does. Then
:534-535 tries to append `[report truncated]`, but `put()`'s first line
(`if (pos >= max - 1) return pos;`) makes the marker dead code. A truncated
`config-report.txt` — the file the whole support story leans on — looks
complete. *Do:* reserve marker space up front, or track an overflow flag; add
a harness case with CFGREC_MAX findings.

### R14. Player-state writes ignore a full card — [verified]
`FileSaveConfig` returns are unchecked for `classicui_state.cfg`
(chome_lib.cpp:749 — favourites and locks), `classicui_recent.cfg` (:693), the
session record (chome_ui.cpp:566) and `classicui_coreopts.cfg`
(chome_core.cpp:383 — per-game options). On a full card a favourite toggle
looks accepted and is gone at reboot. All fail safe to the previous file. The
ini writer, index cache and keystores all check — these four predate the
standard. *Do:* check, and reuse the amber footer to say "the card is full".

### R15. Smaller, worth a line each
- **[verified]** `ss_urlenc` (chome_ss.cpp:256) truncates silently; a long
  all-special-character ScreenScraper password percent-encodes past
  `e_userpass[192]` and drops a character — auth fails with nothing in any log
  saying why. Refuse on truncation instead.
- **[verified]** `user_io_get_confstr()` returns NULL for a zero-length item
  (user_io.cpp:3094), so an empty `;;` field in a CONF_STR ends
  `core_owns_snac()`'s scan early (snacpad.cpp:354) — its `if (!*line)
  continue;` is unreachable. No core is known to emit one; if one ever does,
  SNAC options after the gap go unseen and both readers could drive the port.
  Cheap to make robust now.
- **[verified]** `pad_create()` failure (no `/dev/uinput`) is retried — and
  logged — every 2 ms while a pad is present (snacpad.cpp:102-107 via
  :182-185): 500 lines/sec into the log, the same class as the 257 MB
  debug.txt incident video.cpp already guards against.
- **[verified]** `stub_vars[]` (test/stubs.cpp:170-189) is a hand-copied
  17-row subset of cfg.cpp's table with no drift guard; it already lacks
  `SNAC_*`, `MENU_PLAYER`, `FB_TERMINAL_VGA`, so a cfgrec test touching those
  names would call them typos. The suite documents the trap honestly
  (:165-168); a build-time count/name cross-check would close it.
- **[verified]** harness.cpp:26-31 claims the shared-config section uses "the
  firmware's own bit parser rather than a copy" — but `user_io_status_bits()`
  in stubs.cpp:981-1037 *is* a copy (its own comment says so), and
  `user_io_status_mask()` returns a constant 3. The comment and the stub
  cannot both be right.
- **[verified]** `run.sh` runs `apt-get update/install` in mutable
  `ubuntu:20.04` on every invocation — network-dependent, unpinned compiler
  and imlib2 (whose resampler several exact-pixel checks are hostage to), and
  20.04 is past standard support. Also, under `set -e` a failing test run
  aborts before the PNG copy-out, so diagnostic frames are lost exactly on
  failing runs. Pin an image with the packages baked in; copy PNGs
  unconditionally.
- **[suspected]** a volume label containing `|` splits the disc state line
  and truncates the on-screen label (chome_disc.cpp:259-263 vs :1172).
  Cosmetic.
- **[verified]** a curl fetch started from the in-game menu and abandoned
  when the menu closes is reaped only when the menu next opens
  (chome_art.cpp:1538-1566 polled only from `art_step()`); one zombie + one
  `/tmp` PNG, bounded.

## 3. Reliability

The answer to "is the code reliable" is yes, with the three exceptions above
(R1-R3), and the shape of the exceptions is informative: none of them is
carelessness. R1 is a fixed bug whose twin was never hunted; R2 is one
lifecycle discipline (spawning) done well and its other half (reaping) done
nowhere; R3 is a correct design (sliced scanning) with a slice size nobody
measured. The codebase's failure mode is *a rule applied everywhere except one
last site* — which is the best failure mode to have, because the fix is
mechanical once named.

What the audits did **not** find matters as much: no buffer overflow (all
string builds are `snprintf`), no leak in the render path (every `opendir`,
Imlib2 handle and FILE* was traced closed on every branch; the caches are
byte-budgeted with eviction — art 24 MB, disc rotation 6.4 MB with documented
degradation), no per-frame memory growth, no unrecoverable UI state (every
screen was traced for an exit; the OSD handoff has a timeout precisely so a
core that never shows the OSD cannot strand the player). Error paths facing
the outside world are unusually honest: the rip module checks `fclose` where
data integrity depends on it, zero-fills unreadable sectors and *says so*,
survives a mid-copy USB reset by waiting, and stages into a hidden folder
renamed into place so a power cut leaves nothing; the Wi-Fi join keeps the old
config in memory and rolls back on failure, and tells the truth when the
rollback itself fails. The ini writer (chome_ini.cpp:357-540) is the strongest
code reviewed: backup-first-or-abort, byte-spliced CRLF preservation, replace
in every section *plus* fresh-`[MiSTer]` append, tmp+rename+sync — every trap
in CLAUDE.md designed against in code. Secret hygiene is end-to-end: curl gets
credentials via `-K -` on a pipe (never argv), reply files are 0600 and
unlinked at parse, and all three printers route through `ini_loggable()`.

The busy-poll idle fix (usleep in scheduler.cpp:86-108, gated on
`chome_core_idle() && !menu_mgl_busy()`) is well-reasoned and self-documenting,
including the residual risk it names: a CD core left streaming behind the menu
now gets serviced at ~1 kHz. That is stated, not tested — it is a device
question (§10).

## 4. Test coverage — do we have enough tests?

2425 checks, 0 failures, reproduced here today. Coverage is heavy where the
logic is heavy — ScreenScraper client and throttle ladder (~350 checks), rip
format and screen (~180), core options across five real CONF_STR idioms,
library index/views/variants, the ini writer round-trips ("no stray line
touched"), config report (84), typography and marquee. The SNAC arbitration
section is a model: it asserts the *release* of the port mid-session, not just
acquisition, and its decoys ("SNAC MemCard", "SNAC Compare") encode the exact
false-positive the string match invites.

Where it is thin, verifiably: **`chome_bt.cpp` has zero checks and zero
harness references** — 813 lines of fork/exec process management, the exact
genre R2 lives in, wholly unexercised. `chome_net.cpp` (873 lines, same genre)
has four checks. The uinput half of `snacpad.cpp` (`pad_create`/`pad_update`/
axis decode/hot-unplug) is untested — acknowledged in the code, since a
container has no `/dev/uinput`, but the *decision logic* feeding uinput
(button diffing, hat synthesis, the Select+Start combo edge) is pure and could
run against a recorded-events fake. And by construction the harness cannot see
cfg.cpp, menu.cpp, user_io.cpp, input.cpp — which is exactly where this fork's
shared-file risk lives (§9); the 332 lines added to input.cpp are tested only
by the device.

So: **enough tests for the module, not yet for the seams.** The three seams
that matter — input.cpp's pad gate, cfg.cpp's parse events into cfgrec, and
the status-bit decoding the stubs *copy* rather than share — are each one
drifted duplicate away from a green suite and a broken device. The cheapest
insurance is not more harness: it is compiling one more real file into it
where feasible (cfgrec's producer events could be replayed from a recorded
real parse), and object-level checks (`nm`) where not, which the project
already invented for the ScreenScraper redaction.

## 5. Test quality

High. The things that make suites rot are mostly absent: no golden hash
constants (hashes are differential within a run); geometry is read from
`theme_get()` rather than restated; the stubs are adversarial on purpose and
say so (`menu_key_set` deliberately does not raise `osd_visible` because the
author sabotaged a fix and watched everything still pass — stubs.cpp:1296-1305;
the optmap is keyed on (spec, ex) specifically so the `o`/`O` bug cannot hide,
with a run-end assert that the map never silently filled). The
fix-ships-with-its-test habit is confirmed across history, not just recently:
dd1487b, c55eadf, 3e67e9a, 5e3c27e, ecdce4c, 877bbc6, 57b200a all touch
harness/stubs in the fixing commit; the sole exception (d02939c, the cfg.cpp
password redaction) is the file the harness cannot compile, proven instead at
the object level — the right call, documented in CLAUDE.md.

Weaknesses, honestly: R4 (the guard hole) is the big one. Beyond it, the suite
is a single 21.7k-line `main()` with at least fifteen documented "directly
after it, because it leaves exactly the state" ordering dependencies — one
mid-run failure cascades into misleading reds, and sections reset by
convention (`chome_leave()` + KEY_MENU), not by enforced teardown. A handful
of checks mirror implementation arithmetic (`covers_rect`'s "constants are
draw_covers()'s and have to move with it") — they catch accidental change and
wave through coordinated wrong change. And several exact-pixel thresholds are
hostage to the unpinned imlib2 (R15). None of this is rot yet; all of it is
the kind of debt that converts to rot when the file doubles again. Splitting
the harness into section files with a shared reset fixture is a mechanical
refactor that pays for itself the first time a failure cascades.

## 6. The testing procedure, assessed as a procedure

The hypothesis — Mac first, device for FPGA/analog/SNAC/CPU — is the right
procedure for a one-developer project with one device, and it is unusually
well *institutionalised* rather than merely practised: CLAUDE.md defines
"done" to include "anything the harness cannot reach either goes to the device
or is reported as unverified, in those words"; TEST-PLAN.md is a scripted
device session with expected log lines and "no change is a result"; the
capture tooling (fbgrab/keyinj) and its traps are documented; device tests
produce archived screenshots. The harness-first split is drawn in the right
place — layout, copy, state machines, protocol clients on the Mac; timing,
electrical behaviour, video modes, real drives on the device.

Three structural weaknesses:

1. **No CI.** The suite runs when someone remembers. The Docker harness is one
   `workflow_dispatch`+push job on a GitHub runner (it needs no ARM toolchain);
   the ARM cross-compile is a second job. With no reviewer, an unforgetting
   gate is worth more here than in a team repo. Pinning the image (R15) is a
   prerequisite and independently worthwhile.
2. **The device fleet is one analog-only board**, so an entire first-class
   output path (HDMI 720p/1080p, `vga_scaler=1`, the halfres upscale's actual
   look) has never been on glass — while the user docs claim it has (R7). The
   procedure handles this correctly in TEST-PLAN (Part B exists, gated on
   plugging in a screen); the docs got ahead of it. Either borrow an HDMI
   panel for one Part-B session or soften the GUIDE row until then.
3. **Proving a fix can fail is a habit, not a mechanism.** It lives in
   comments and discipline; nothing re-runs the reverted-fix experiment. Where
   it was done, it is documented; where it was skipped, nothing notices. The
   two guard holes in R4 are exactly what a "make the guard fail on purpose"
   pass would have caught — the habit was applied to production fixes but not
   to the guards themselves.

## 7. UI/UX

Walked as a player, via the 322 rendered frames (240p set prioritised) and the
docs. The core loop is genuinely controller-first: shelf → game → suspend
points → back is all pad, all legible, with button glyphs matching the pad in
hand (including remaps — `input_menu_key_btn()` exists so a remapped pad is
described truthfully, which almost nobody does). The two-press pattern for
every destructive act is consistent. The Wi-Fi and pairing screens show
progress states so slow looks busy, not broken. The controller tester is
excellent. "Best Settings" showing the exact ini lines it would write, with a
backup and a second press, is the most trustworthy settings screen I have seen
on this class of device. The config-report answer to "the shelf never came up"
— a plain file on the card, written without consulting `debug=` — is the
correct design for the failure it serves, and the Options footer naming it in
amber closes the loop when the shelf *is* up.

240p is near-first-class, with honest deliberate cuts (Display hidden, with
the reason documented; legend entries dropped by measured fit). Points of
friction, smallest first:

- The 240p shelf legend drops **Sort** (Select) and the position counter when
  they do not fit — the feature exists and is undiscoverable exactly where
  libraries feel longest. Consider rotating legend entries the way the
  marquee rotates text, or folding Sort into the menu bar at `lo`.
- The OSK draws its own key legend *and* the underlying screen's legend
  remains visible below (wifi-2-password.png) — two competing button bars
  during the highest-concentration task. Dim or suppress the lower one.
- A disc with no title-table entry shows `SLUS-00626` on a shelf of real
  names (disc-9-dialog.png). The table ships in the release archive, but the
  failure is silent: the dialog could footnote "name unknown — see
  disctitles.txt" once, the way other screens footnote their reports.
- R9 (stale armed confirms) reads as "the UI ignored my press" — a
  correctness bug wearing a UX costume.
- The in-game menu over a physical-disc game has a black surround by
  design/known limitation; the release notes say so, which is the right
  interim answer.

## 8. Labels and copy

The copy is a genuine strength — plain, concrete, jargon-refusing ("Hold the
game still while the menu is open"; "Always shut down here rather than pulling
the plug"), and the long/short legend pairs ("Suspend Points"/"Saves",
"Favourite"/"Fav") are a deliberate system, not drift. The MiSTer.ini template
comments and the GUIDE's CRT tables are documentation users will actually
survive on. Nits: "B START" on the shelf legend uses START as a verb next to
pads that have a physical Start button doing something else — "PLAY" is
already used on the disc dialog and is unambiguous; the 240p abbreviation
"SAVES" for suspend points is the one place the renamed concept leaks its old
name back in; and the errors surfaced from helpers ("Check the password and
try again" when the real failure was a missing `iw` binary —
chome_net.cpp:856) occasionally diagnose the common cause rather than the
actual one. All small. The stale-comment cluster (R7) is the only copy debt
that can cause real harm, and it is developer-facing.

## 9. Upstream divergence

Measured today: `git diff --shortstat af770c5..classic-ui` = **229 files,
+95,849 / −89**; 391 commits. The brief's figures (292 files, +113k/−9k, 417
commits) do not match this branch at this base — in particular **the 9k
deletions do not exist; deletions against upstream are 89 lines.** The
divergence is almost purely additive, which is the single most important fact
for future merges.

The shared-file changes (~1,400 lines across twelve files) are disciplined:
nearly everything is gated on `chome_active()`/`cfg.classicui` or a request
the front-end makes only while on screen, and every change carries a
paragraph explaining itself — the `menu_mgl_busy()` comment in menu.cpp that
documents *two rejected wrong fixes* is the standard other forks should be
held to. UPSTREAM.md is the right instrument and needs the R7 refresh.

For a user with `classicui=0`, stock behaviour changes in exactly these ways
(all verified in the diff):

1. The menu button no longer auto-repeats when held (menu.cpp:610-614) — a
   fix; upstream-worthy.
2. `vga_nag()` fires on `video_fb_terminal() && !get_vga_fb()` instead of
   `video_fb_state()` (menu.cpp:868-888) — strictly more correct, but it is a
   stock-visible change and should be in UPSTREAM.md's "the one exception"
   list, which currently names only the pop-up suppressions.
3. Neo Geo CD MGLs with relative paths now resolve (menu.cpp:2837-2863) — a
   fix; upstream-worthy.
4. `FileGenerateSavestatePath()` no longer writes through NULL for
   extensionless names (file_io.cpp:1016-1034) — a latent upstream crash
   fixed; upstream-worthy, and the best candidate to open with.
5. `classicui/config-report.txt` is written on every menu-core boot,
   unconditionally by design (user_io.cpp:1473-1490). Deliberate and argued;
   it is still a new file appearing on the card of someone who turned
   everything off — worth one line in the release notes.
6. `cfg_print()`/ini debug redact `classicui_ss_pass` (cfg.cpp:959-963) —
   strictly safer.
7. `snacpad_poll()` runs on 8BIT cores (user_io.cpp:3267) — inert until
   `snac_pad=1`, and with it off it returns before touching SPI (verified,
   snacpad.cpp:515-516).

Merge-conflict exposure concentrates where upstream churns: `joy_digital()`
and the `input_cb()` key path in input.cpp, `process_ss()` in user_io.cpp
(statics renamed and hoisted — a whole-function conflict on any upstream
touch), and `video_fb_config()`. That is the cost of the features and it is
paid knowingly; the UPSTREAM.md habit is the mitigation and it works only if
kept current. `snac-pr` as a minimal branch for upstreaming is the right
structure; items 1/3/4 above belong on it or beside it.

## 10. The SNAC half

The arbitration design is right, and better than the setting it replaced.
`core_owns_snac()` (snacpad.cpp:348-393) derives ownership from the core's own
CONF_STR — no table of core names to maintain, generalises to consoles that do
not exist yet, errs toward "the core owns it" (dead port, not double-driven
port — the correct fail direction, argued in the comment), reads only the
in-memory `cfgstr`/`cur_status` shadows (verified: user_io.cpp:3078-3099 —
zero SPI per poll), and honours the `o`/`O` second-status-word distinction.
Re-deriving every 2 ms instead of holding a settled state eliminated a probe
window and five variables; the residual "one corrupt pad frame during a
hand-over" is stated. The ID whitelist (0x41/0x73/0x53) matches exactly what
the fabric reader can decode (psx_snac_pad.sv header), and the refusal path
turns an unknown adapter into a logged ID instead of a phantom pad with every
button held — the SuperDock bypass-switch case is designed for, and
`snac_device=1` exists for the case that cannot be inferred. The harness now
covers acquisition, release, decoys, bad-ID refusal and recovery against five
real CONF_STR idioms.

Failure modes not yet covered, in the order I would worry:

1. **Electrical/two-master windows are untestable from here** — the enable
   handshake around a mid-game `Pad1` flip is modelled, never scoped. One
   device session with a logic probe (or just a pad and patience) settles it.
2. The empty-confstr-field early-break (R15) is the one *logic* hole found in
   the arbitration; cheap to close before a core ever emits one.
3. Hot-unplug and the digital↔analog ID transition mid-game exercise
   `pad_destroy`/re-create ordering that only the device runs today.
4. The uinput half is untested and generates log spam at 500 Hz if
   `/dev/uinput` ever fails while a pad is present (R15).
5. `snacpad_poll()` runs only for `CORE_TYPE_8BIT`; Minimig/ST never poll —
   correct today (their frameworks carry no reader) and worth one comment
   line so the gate is not "fixed" into a bug later.

`snac_device` as a description-of-hardware rather than a preference, defaulted
to the zero-config case and never inferable, is well-judged, and the
deprecation of `snac_psx*` with a printed migration note (cfg.cpp:774-790) is
how settings should be retired.

## 11. Missing features

Present and working, for the record: favourites, Recently Played (as a view),
sort (see R8), letter-jump, versions/multi-disc as one card, per-game core
options with promote-to-shared, resume/suspend points with pictures, physical
disc with rip, art scraping with three fallback rungs, Wi-Fi, BT pairing,
controller test, fonts/typography, power screen. Deliberate absences with
written reasons (README "Deliberately not implemented"): bezels, rewind, UI
sound, attract mode, first-run wizard, aspect controls.

Absences a player will actually feel, in order:

1. **Search.** On the stated target (a big shelf, a couch, no keyboard),
   letter-jump is the only tool, and it walks one dimension. The OSK already
   exists; a search that filters the shelf as you type is the single
   highest-value missing feature and needs no new infrastructure.
2. **Game metadata on the shelf.** `chome_item` has year/publisher/players
   fields that nothing fills, and the gamelist.xml already on scraped cards
   carries descriptions the reader deliberately ignores. The refusal is
   principled ("titles come from filenames") but half the audience arrives
   with a scraped card; one optional line of year/players under the title
   would use data already paid for. Low effort, visible payoff.
3. **Collections/genre** beyond Favourites — felt on 1000+ shelves, and the
   sort/view machinery would carry it. Medium effort.
4. **A second theme / dark-light or colour accent** — the single grey theme
   is handsome but fixed; `chome_theme.cpp` is small and centralised, so this
   is cheaper than it looks. Cosmetic, optional.
5. Screensaver/attract: stock `video_off` covers burn-in; a shelf attract
   mode is a nice-to-have, already argued out of scope.
6. Multiple users: correctly skipped for this device class.

## 12. What I could not assess, and what it would take

- **Anything electrical or timed**: SNAC bus behaviour during ownership
  hand-over, the fabric reader against real pads/adapters, frame times at
  720p vs 240p, the 1 kHz-serviced streaming-core case
  (chome_ui.cpp:12843-12847 names it). Needs the device; TEST-PLAN.md already
  scripts most of it.
- **The two open device bugs** (R6): the next scripted session's Part A.
- **HDMI on real glass** (R7/§6): one session with a borrowed panel runs
  TEST-PLAN Part B and C as written.
- **R3's magnitude**: time Options ▸ Rescan Library on the device against a
  2-3000-zip folder; the fix is worth doing regardless, the number decides
  its urgency.
- **R10**: launch one `&`-named ROM. Five minutes.
- **Zombie accumulation in practice** (R2): `ls /proc/*/stat`-count after an
  evening of disc swaps and pairings; the code reading is sufficient to fix
  it without this, but the number makes the release-note honest.
- **Real-world Wi-Fi/BT hardware behaviour** (R11, and `chome_bt` having zero
  checks): the harness cannot fake a dongle; the device sessions should
  include one deliberate mid-join unplug and one mid-pair cancel while
  watching the process table.
- **A 16 MB gamelist.xml first-parse stall** (suspected, size-dependent):
  copy one real scraped card in and scroll; A8.2 in TEST-PLAN already asks
  for exactly this number.
